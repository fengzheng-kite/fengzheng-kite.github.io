大模型正在进入机器人控制系统，但模型能力越强，推理往往也越慢。对于聊天机器人，多等待几百毫秒可能只影响体验；对于正在运动的机器人，这段时间却可能意味着动作停顿、轨迹跳变，甚至错过与环境交互的最佳时机。

Real-Time Chunking（RTC）试图解决的正是这个问题：让机器人在执行当前动作的同时，后台生成下一段动作，并让新旧轨迹自然衔接。

本文不讨论某一种机器人或某个具体任务，而是从工程部署的角度，介绍如何理解和搭建一套通用的 Infra-RTC。

## Action Chunking 还不够

许多视觉—语言—动作模型不会一次只预测一个动作，而是一次生成一段未来动作，也就是一个 action chunk。

这样做的好处很明显：模型不需要跟控制器保持相同的推理频率。控制器可以先缓存一段动作，再按照自己的频率逐步执行。

但普通的 action chunking 仍然存在两个问题。

第一个问题是等待。当一段动作执行完，而下一次推理还没有完成时，机器人会短暂停住。模型越大、网络越远，这个停顿越明显。

第二个问题是跳变。前后两个动作块通常根据不同时间的观测独立生成，它们可能选择了不同的运动策略。直接从旧动作块切换到新动作块，容易在边界处产生不连续。

一种直观做法是对两段动作取平均，但平均后的轨迹不一定属于模型学到的有效行为。如果两次预测原本对应两种不同策略，平均甚至可能得到两边都不成立的动作。

## RTC 的核心思想

[RTC 原论文](https://www.physicalintelligence.company/download/real_time_chunking.pdf)将异步动作生成描述为一个 inpainting 问题。

当模型开始生成下一段动作时，机器人仍在执行上一段动作。因此，新动作块开头的一部分实际上已经由旧计划决定：这些动作要么正在执行，要么在推理完成前必然会执行。RTC 将这部分动作作为约束保留下来，再让模型生成更远的未来。

可以把它理解为：

- 近处的动作已经承诺，不能随意改变；
- 中间的动作尽量延续旧计划，但允许逐渐调整；
- 更远的动作根据最新观测重新规划。

因此，RTC 不只是“提前请求下一段动作”。它还要求新动作在生成阶段就与旧轨迹保持一致。异步调度解决等待问题，动作前缀约束解决交接问题，两者缺一不可。

```text
旧动作块：执行中 ────────────────►
                    │
                    └── 后台生成新动作块
                             │
新动作块：        对齐旧轨迹 ────► 规划新未来
```

## 什么是 Infra-RTC

RTC 是推理算法，而 Infra-RTC 是让它能够稳定运行的工程基础设施。

一套完整的 Infra-RTC 通常包含四个部分：

1. 能够接受历史动作约束的策略模型；
2. 在后台运行模型推理的异步执行器；
3. 管理当前动作块和下一动作块的调度器；
4. 负责校验、监控、超时和安全停止的运行时机制。

这里最容易产生误解的一点是：普通模型外面套一个异步线程，并不会自动变成 RTC。

真正的 RTC 需要底层策略在生成下一段轨迹时，能够使用上一段轨迹的剩余部分作为条件。对于 diffusion 或 flow-matching 模型，这通常通过冻结部分动作、对重叠区域施加引导，再对远期动作重新生成来实现。

## 一次 RTC 循环是怎样运行的

RTC 的运行过程可以概括为以下几步。

首先，系统根据当前观测生成第一段动作。这一步没有历史轨迹可参考，因此与普通 action chunking 类似。

接下来，控制器开始逐步执行这段动作。执行到预设位置后，调度器不会等待整段动作耗尽，而是立即获取最新观测，并在后台请求下一段动作。

推理期间，控制循环继续消费旧动作块。模型则使用旧动作中尚未执行的部分作为约束，生成一段能够自然延续当前运动的新轨迹。

新结果返回后，调度器跳过其中与推理延迟对应的部分，从正确的时间位置开始执行。随后系统再次触发后台推理，整个过程形成连续流水线。

```text
执行当前动作 ──► 发起后台推理 ──► 继续执行旧动作 ──► 切换新动作
                      │                                      │
                      └──── 模型生成下一段连续轨迹 ──────────┘
```

理想情况下，机器人不需要停下来等待模型，同时新旧动作块也不会发生明显跳变。

## 部署时最重要的不是参数，而是时间关系

RTC 通常会涉及预测长度、预取位置和延迟偏移等配置。具体数字取决于模型速度、控制频率和任务特性，没有一组参数能够适用于所有系统。

相比记住某些固定值，更重要的是理解三个时间关系：

- 当前动作缓存必须足够长，能够覆盖一次推理及其抖动；
- 后台请求必须足够早，不能等到动作即将耗尽才开始；
- 新动作的起始位置必须与推理期间已经执行的时间对齐。

参数选择不能只看平均推理耗时。真实系统还会受到网络抖动、GPU 排队、图像预处理和首次编译的影响。更可靠的做法是统计推理延迟的分布，并为尾延迟留出余量。

## Warmup 为什么很重要

许多模型的第一次请求明显慢于后续请求。JAX 编译、CUDA 初始化、权重物化和缓存建立都可能发生在首次调用中。

对于 RTC，仅仅预热普通推理路径还不够。带历史动作约束的 RTC 推理可能使用不同的张量形状和计算路径，因此也应该单独预热。

一个稳妥的启动过程是：先完成普通动作生成，再用它构造一次历史动作条件，完整执行一轮 RTC 推理。只有两条路径都通过后，控制系统才进入真实运行状态。

## 避免“看起来异步，实际上仍然阻塞”

这是 RTC 部署中最常见的问题之一。

即使程序创建了后台任务，只要网络接收、模型调用或数据预处理仍在控制线程中同步执行，控制循环就可能被阻塞。最终表现是日志显示已经启用异步模式，但动作输出仍会周期性停顿。

真正的异步部署需要确保：

- 模型推理不占用控制循环；
- 网络等待不会阻塞动作发布；
- 同一时间只保留一个待完成的推理请求；
- 推理结果与发起请求时的观测正确关联。

最后一点尤其重要。后台结果返回时，系统可能已经接收了更新的传感器数据。推理结果必须属于请求发起时的观测，而不是响应到达时的最新观测，否则日志、延迟分析和动作归因都会出错。

## 需要明确区分两种动作空间

一些 RTC 实现会同时返回两种动作：一种是最终发送给机器人执行的动作，另一种是模型内部用于下一轮条件生成的动作表示。

两者可能拥有不同的维度、归一化方式和语义。部署时必须明确：

- 哪一组动作可以直接发送给控制器；
- 哪一组动作只能用于构造下一次 RTC 条件；
- 历史动作的时间对齐和补齐方式是什么。

不能因为它们都被称为“动作”就互相替代。维度不一致会立即报错，语义不一致则可能产生更隐蔽的错误。

## 必须保留的安全边界

RTC 可以隐藏延迟，但不能消除延迟。当模型长时间没有返回结果时，当前动作缓存最终仍会耗尽。

此时系统必须进入明确的安全路径，例如停止、保持当前位置或交给底层控制器接管。悄悄重复最后一个动作，或者继续访问已经耗尽的缓存，都可能带来不可预测的行为。

一套可靠的 RTC 运行时至少应该具备：

- 动作块长度和维度校验；
- 客户端与服务端配置握手；
- 单请求并发约束；
- 推理超时与缓存耗尽检测；
- 退出时取消后台任务；
- 与具体机器人平台匹配的安全停止机制。

RTC 负责轨迹生成和交接连续性，但它不能替代关节限位、速度限制、碰撞保护和急停等底层安全机制。

## 如何证明 RTC 确实生效

“机器人看起来更顺”只能作为直观感受，不能单独证明 RTC 部署正确。

首先要证明推理与执行发生了重叠。后台请求进行期间，动作索引和动作发布时间应该继续前进。如果每次请求期间动作日志都停止，系统仍然是同步执行。

其次要验证动作块交接。每次新旧 chunk 切换时，应记录旧块最后动作、新块第一动作以及对应时间，从而分析边界跳变和指令连续性。

最后还要观察任务层效果。RTC 的价值不仅是减少停顿，也应该体现在完成时间、成功率、异常停止次数和对推理抖动的鲁棒性上。

建议至少关注四类指标：

1. 推理延迟的均值、尾部和最大值；
2. 观测到动作发布的端到端延迟；
3. 动作块边界的跳变与指令平滑性；
4. 任务成功率和完成时间。

如果要讨论机械臂真实速度、加速度或 jerk，还需要足够频率的反馈数据以及明确的滤波和数值微分方法。仅根据低频动作指令，不能直接声称测得了机器人真实动力学指标。

## RTC 适合哪些系统

RTC 特别适合以下场景：

- 模型一次生成一段连续动作；
- 模型推理明显慢于控制频率；
- 任务需要持续运动，无法接受周期性停顿；
- 新旧计划可能发生策略切换，简单平均不可靠；
- 策略属于能够执行条件生成的 diffusion 或 flow-matching 模型。

如果模型本身足够快，可以在每个控制周期内完成推理，RTC 的收益会比较有限。如果策略无法利用历史动作条件，系统最多只能实现普通异步缓存，无法获得 RTC 的生成阶段连续性。

## Inference-time RTC 与 Training-time RTC

本文主要讨论 inference-time RTC。它在推理过程中使用旧动作对新动作进行 inpainting，因此可以在不重新训练基础策略的情况下加入异步执行能力，但会增加推理阶段的计算量。

[后续工作](https://arxiv.org/abs/2512.05964)提出了 training-time action conditioning：在训练阶段模拟推理延迟，让模型学会直接根据动作前缀继续生成。这样可以减少部署时的额外计算，但需要相应的训练流程和模型能力。

两种方法目标相近，协议和模型假设却不同。部署时应该从模型训练方式开始确认所使用的 RTC 类型，不能只替换客户端开关或请求字段。

## 结语

RTC 解决的不是单纯的“模型推理太慢”，而是高延迟智能模型与连续物理控制之间的时间矛盾。

它让机器人在执行旧计划时生成新计划，再通过动作前缀约束，让新轨迹自然接住已经发生的运动。围绕这一过程搭建的异步调度、缓存管理、时间对齐、运行时校验、可观测性和安全退出，共同组成了 Infra-RTC。

一套好的 Infra-RTC 不应该绑定某台机器人。只要模型能够接受历史动作条件，控制器能够管理动作缓存，系统就可以将相同的思路迁移到不同平台。真正需要被复用的，不是某一组参数，而是“边执行、边推理、带约束地重新规划”这一完整闭环。
